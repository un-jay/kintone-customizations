# handwriting-input 個別仕様

全体共通の開発方針は [ルートのCLAUDE.md](../../CLAUDE.md) を参照。ここには本カスタマイズ固有の仕様のみを記載する。バックエンド(Azure OCR中継)の仕様は [gas/README.md](./gas/README.md) を参照。

## 背景・要求

製造業の現場では、タブレットへの直接入力に抵抗があり、紙に手書きしたメモをそのまま使い続けている。このカスタマイズは、**紙に手書きされたメモを写真で撮影し、文字を自動認識してkintoneのフィールドへ転記する**。現場の作業者は「撮影してボタンを押すだけ」で済み、手書きの習慣を変える必要がない。

## 方式決定の経緯(重要・変更しないこと)

以下は実装前の検証で判明した制約であり、方針を再検討する際は必ず踏まえること。

- **ブラウザ内蔵の無料OCR(Tesseract.js)は実用に耐えない**。マス目に区切って1文字ずつ認識させる方式を実機相当の検証で試したが、単純な英字ですら誤認識し、空白のマスにも幻の文字を検出した。日本語の手書き文字ではさらに精度が悪化することが予想される
- **OS標準の手書き認識(Windows Ink/iPadのScribble等)は不採用**。これは「タブレット上に直接ペンで書く」方式に対応するものだが、本カスタマイズの要求は「紙に書かれた既存のメモを読み取る」ことであり、前提が異なる
- 上記の理由から、**Azure AI Vision(Image Analysis 4.0のReadOCR機能)** をバックエンド(GAS Web App経由)で呼び出す方式を採用した。手書き日本語に対応しており、無料枠(F0相当、5,000件/月)を超えてもエラーになるだけで自動課金されない設計のため、Google Cloud Vision(1,000件/月を超えると自動課金)より安全に「実質無料」を維持できる

## 全体構成

```
紙のメモを撮影(kintoneカスタマイズ)
  → 写真をBase64化してGAS Web Appへ送信
  → GASがAzure AI Vision(Read機能)を呼び出し、認識結果を整形して返す
  → kintone側で認識結果をテキストフィールドへ反映(作業者が確認・修正可能)
  → 写真そのものも添付ファイルフィールドへ原本として保存
```

**AzureのAPIキーはGAS側のスクリプトプロパティにのみ保存し、ブラウザ側のJavaScriptには一切含めない**（ブラウザ側に置くとページソースやネットワークタブから盗まれるため）。GAS Web Appは、キーを漏らさずAzureへ中継する役割に専念する。

### reminder-notifyとの違い(重要)

reminder-notifyのGASは、送信元メールアドレスを顧客自身のものにする必要があったため、**顧客のGoogleアカウント上に**GASプロジェクトを作成する構成だった。

本カスタマイズのGAS Web Appは、Azure APIキーを中継するだけのステートレスな処理であり、送信元アカウントのような制約が無い。そのため、**開発側(納品元)のGoogleアカウント上に1つだけ作成し、複数の顧客・複数のkintone環境から共通で呼び出せる**構成にできる。顧客側はAzure/GASの存在を意識する必要が無い（Web AppのURLと共有シークレットだけをkintone側に設定する）。

## 対象アプリのフィールドコード（固定）

`src/desktop.js`の`HANDWRITING_TARGETS`定数に、対象フィールドの組を配列で定義する（1アプリに複数の手書き対象フィールドを設定できる）。デモアプリでの具体例は[README.md](./README.md)を参照。

各要素の構成:

| キー         | 説明                                                                 |
| ------------ | -------------------------------------------------------------------- |
| `textField`  | 認識結果を書き込む文字列（複数行）フィールドのフィールドコード       |
| `imageField` | 撮影した写真の原本を保存する添付ファイルフィールドのフィールドコード |
| `spaceId`    | 「手書きメモを読み取る」ボタンを設置するスペースフィールドの要素ID   |
| `label`      | ボタンに表示する対象名（例: 「作業内容」）                           |

**注意**: `kintone.app.record.getFieldElement()`はレコード追加・編集画面では使用できない（レコード詳細画面専用のAPI）。そのため、ボタンの設置には`kintone.app.record.getSpaceElement()`を使用する。対象アプリの該当フィールードの近くに、あらかじめ指定した要素IDのスペースフィールドを配置しておく必要がある。

## 動作フロー

1. レコード追加・編集画面表示時（PC/モバイル。`app.record.*.show`と`mobile.app.record.*.show`の両方を登録）に、`HANDWRITING_TARGETS`の各要素についてスペース要素へボタンを設置する
2. ボタン押下 → 全画面オーバーレイ（独自UI。マス目キャンバスのような複雑なUIのため`kintone.createDialog`ではなく独自のフルスクリーンUIとする）を表示する
3. 写真を撮影または選択する。`<input type="file" accept="image/*" capture="environment">`（「📷 撮影する」。カメラが直接起動する）と、`capture`無しの`<input type="file" accept="image/*">`（「🖼 写真を選ぶ」。写真ライブラリ・ファイルから選択）の2つを使い分ける。「撮影する」はモバイル画面またはタッチ端末（`navigator.maxTouchPoints > 0`）でのみ表示し、PCでは「写真を選ぶ」のみ
4. 撮影した写真をプレビュー表示し、アップロード前にクライアント側でリサイズする（長辺1600px・JPEG品質0.8を目安。現場のネットワークが遅い前提で、送信量を抑えるため）
5. 「文字にする」ボタン → リサイズ後の画像をBase64化し、GAS Web AppへPOSTする（後述のCORS対応が必要）
6. 認識結果を、対象フィールドの**既存の値の末尾に改行を挟んで追記**する形でプレビュー欄（編集可能なテキストエリア）に表示する（1日の中で複数回メモを取り込む運用を想定し、上書きしない）
7. 作業者が内容を確認・修正できる（OCRは完全ではないため、確認前提の「下書き自動作成」という位置付け）
8. 「反映する」ボタン → 写真をkintoneのファイルアップロードAPI(`/k/v1/file.json`)へアップロードしてfileKeyを取得し、`kintone.app.record.set()`で**テキストフィールドのみ**を更新する。fileKeyは`pendingAttachments`に保持しておく
9. オーバーレイを閉じ、成功通知を表示する（この時点では写真はまだ添付されていない。次項参照）
10. 作業者がkintone本来の「保存」ボタンを押し、レコード保存が成功すると発火する`app.record.create.submit.success`/`app.record.edit.submit.success`イベントで、保持しておいたfileKeyをREST API(`kintone.api()`のPUT)により添付ファイルフィールドへ反映する

### なぜ「反映する」の時点で添付ファイルを直接セットしないのか(重要)

公式ドキュメント「[レコードに値をセットする](https://cybozu.dev/ja/kintone/docs/js-api/record/set-record-value/)」の制限事項に、**「添付ファイルフィールドでは、レコードの値を書き換えできません」と明記されている**。`kintone.app.record.set()`は添付ファイルフィールドに対して機能しない（実装時に見落とし、実機テストで「写真だけ反映されない」不具合として発覚した）。

添付ファイルフィールドをJavaScriptから更新する唯一の方法は、REST API(`kintone.api()`)で`record.json`をPUTすることだが、これには保存済みレコードの`id`が必要（新規作成画面ではまだ存在しない）。そのため、「反映する」時点ではfileKeyを保持するだけにし、**レコードが実際に保存された後**（`submit.success`イベント）に、`event.recordId`・`event.record.$revision.value`を使ってREST APIで添付ファイルフィールドだけを更新する、という2段階の設計にしている。

## モバイル対応の方針（重要）

`mobile.js`/`mobile.css`を別に作らず、**`desktop.js`/`desktop.css`をPC用・モバイル用の両方にアップロードして共用する**。理由は、処理の大半（画像リサイズ・GAS呼び出し・ファイルアップロード・オーバーレイUI）が共通で、分けると二重管理になるため。

- PC用とモバイル用でkintone JS APIの名前空間だけが異なる（`kintone.app.record.*`/`kintone.showNotification` と `kintone.mobile.app.record.*`/`kintone.mobile.showNotification`、イベント名の`mobile.`接頭辞）。この差は`desktop.js`の`PLATFORM`オブジェクト（`desktop`/`mobile`）に集約し、ハンドラー生成関数（`createShowHandler`/`createSubmitSuccessHandler`）とオーバーレイ処理へ`platform`として渡す。**`kintone.mobile`はPC画面には存在しないため、`PLATFORM`の各関数は呼び出し時に評価する（トップレベルで参照しない）**
- ファイルアップロード（`kintone.api.url('/k/v1/file.json', true)`・`kintone.getRequestToken()`・`kintone.api()`）はモバイルでも同じAPIを使える
- オーバーレイは`position: fixed`の全画面表示。モバイルでは`100dvh`（アドレスバー分で下が切れない）・セーフエリア（ノッチ・ホームバー）・スマホ幅（600px以下）でのボタン拡大、テキストエリアの`font-size: 16px`（iOS Safariの入力時自動ズーム防止）に対応している。オーバーレイ表示中は`document.body.style.overflow = 'hidden'`で背面のスクロールを止め、閉じるときに元の値へ戻す
- モバイル用のレコード画面にも、PCと同じスペースフィールド（`HANDWRITING_TARGETS`の`spaceId`）が表示される。スペースフィールドはフォームの設定で、PC・モバイル共通

## GAS Web Appとの通信（CORS注意）

GAS Web Appは`doPost`でOPTIONSプリフライトを処理できないため、プリフライトが発生しない`Content-Type: text/plain;charset=utf-8`でPOSTし、GAS側で`e.postData.contents`をJSONとして手動パースする（実体はJSONだが、ヘッダー上は`text/plain`にすることでブラウザのプリフライトを回避する、GAS Web Appの定番の回避策）。

GAS Web Appは仕様上、`doPost`のレスポンスに任意のHTTPステータスコードを設定できない（常に200を返す）。そのため、成功/失敗はHTTPステータスではなく、レスポンスJSONの`ok`フィールドで判定する。

リクエストボディには共有シークレット(`sharedSecret`)を含め、GAS側で一致を確認してから処理する（Web AppのURLが漏れても、無関係な第三者がAzureの無料枠を消費できないようにするための簡易な防御。ブラウザ側JSに埋め込む値のため厳密な秘匿ではない点に注意。真の防御はAzureキー自体をブラウザに一切渡さないことにある）。

## エラーハンドリング

- 対象のスペースフィールドが見つからない場合（要素IDの設定ミス等）は、その対象だけスキップし、コンソールへ警告を出す（他の対象への影響を避ける）
- 写真が選択されていない状態で「文字にする」を押すとエラー通知を表示する
- GAS Web Appの呼び出し自体が失敗した場合（ネットワークエラー・URL未設定等）、およびGASからのレスポンスが`ok: false`の場合は、エラー内容をそのまま通知で表示する（Azure側のエラーメッセージも含めることで、バックエンド側の対応者が原因を特定しやすくする）
- 認識結果が空文字だった場合も「反映する」は可能（作業者が手動で全文入力するケースを妨げないため）
- レコードの保存自体は成功したが、保存後の添付ファイル反映(REST API PUT)が失敗した場合は、その旨を通知し「手動で添付ファイルフィールドへ写真を追加してください」と案内する（テキストは既に保存済みのため、レコード自体を失敗扱いにはしない）

## APIリクエスト数について

- kintone側カスタマイズは、写真アップロード(`/k/v1/file.json`)を「文字にする」1回の操作につき1回。レコード情報の取得・書き換え(`kintone.app.record.get/set`)はローカルのフォーム状態を操作するのみで、REST APIのリクエスト数にはカウントされない
- 添付ファイルフィールドの反映のため、レコード保存成功時(pendingAttachmentsが1件以上ある場合のみ)に、`record.json`のPUTが1回発生する（複数の対象フィールドに反映していても、1回のPUTにまとめて送信するため保存1回につき最大1回）
- GAS Web AppからAzureへのリクエストは1回の「文字にする」操作につき1回。Azure無料枠(5,000件/月)の消費に直結するため、現場での想定利用件数（1日あたりの手書きメモ取り込み回数 × 稼働日数）が枠に収まるか、導入時に確認すること

## 既知の制約

- ゲストスペース内のアプリでも動作するよう、写真のアップロードURLは`kintone.api.url('/k/v1/file.json', true)`でゲストスペースを自動判定している（[ルートのCLAUDE.md](../../CLAUDE.md#ゲストスペースとセキュアアクセス)参照。ゲストスペースでの実機確認は未実施）。GAS Web App側はkintoneを呼ばない（Azureへ中継するだけ）ため、ゲストスペース・セキュアアクセスの影響を受けない

- カメラ起動には`<input type="file" capture="environment">`を使用するブラウザ標準機能に依存する。対応状況はブラウザに依存するが、主要なモバイルブラウザ（iOS Safari、Android Chrome）では広くサポートされている。**スマートフォンの実機でのカメラ起動・アップロードは未確認**（jsdomでの単体テストのみ）
- モバイルのkintone(ブラウザ版のモバイル画面`/k/m/`・kintoneモバイルアプリ)で読み込まれる。モバイルアプリ内のWebViewでは、カメラ・写真ライブラリへのアクセスがOS/アプリの権限設定に依存するため、導入時に実機で確認すること
- OCRの認識精度は完全ではない。手書きの癖・筆記用具・照明条件により結果が変動するため、反映前に必ず作業者が確認する運用を前提とする
- Azure AI Visionの1リクエストあたりの画像サイズ上限は20MB（クライアント側リサイズにより通常はこれを大きく下回る）
